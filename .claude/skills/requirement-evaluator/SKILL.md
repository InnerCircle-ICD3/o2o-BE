# ddd-rubric SKILL

DDD 관점에서 요구사항(PRD, 사용자 스토리, 기능 명세)을 평가하여 Rich Domain Model 품질과 요구사항 완결성을 점수화합니다.

## 사용법

```
/evaluate-requirements {요구사항}
```

## 기능

사용자가 입력한 요구사항을 2차원 루브릭으로 평가합니다:
- **요구사항 완결성 (5점)**: LLM 코드 생성의 전제 조건 (최우선)
- **DDD 설계 품질 (10점)**: Rich Domain Model 달성도

## 요구사항 형식 자동 감지

| 요구사항 형식 | 평가 체계 |
|-------------|---------|
| **체크리스트 형식** | 1차원만 (도메인 식별, YAGNI, 백엔드 범위, 적절성, 완결성) |
| **PRD/기능 명세 형식** | 2차원 (요구사항 완결성 5점 + DDD 설계 품질 10점) |

### 체크리스트 형식 평가 항목 (5점 만점)

| 항목 | 점수 | 평가 기준 |
|-----|-----|----------|
| 도메인 식별 | 1점 | 도메인이 명확히 식별됨 (payment, subscription, exam) |
| YAGNI 원칙 | 1점 | 현재 플로우에 필요한 요구사항만 포함됨 |
| 백엔드 범위 | 1점 | 백엔드 + 외부API만 포함, 프론트엔드 제외 |
| 도메인별 적절성 | 1점 | 도메인별 필수 요구사항이 적절하게 포함됨 |
| 체크리스트 완결성 | 1점 | 핵심 항목이 구체적으로 명시됨 |

## 2차원 평가 체계

| 차원 | 만점 | 목적 | 비중 |
|-----|-----|------|-----|
| **요구사항 완결성** | 5점 | LLM 코드 생성 전제 조건 | **최우선** |
| **DDD 설계 품질** | 10점 | Rich Domain Model 달성 | 설계 |

## 범위 자동 감지 (Scope Detection)

요구사항에서 핵심 범위를 자동으로 추출하여 YAGNI 원칙을 적용합니다:

| 요구사항 제목 | 범위 | 제외하는 질문 |
|-------------|------|-------------|
| 결제 검증 | Payment 도메인만 | 환불, 갱신 |
| 구독 생성 | Subscription 도메인만 | 갱신, 취소 |
| 구독 결제 플로우 | Payment + Subscription | 갱신, 환불 |
| 모의고사 생성 | Exam 도메인만 | 재시작, 삭제 |
| 답안 제출 | ExamUserAnswer 도메인만 | 채점, 결과 조회 |

**YAGNI 원칙**: 미래의 기능(갱신, 환불, 취소, 재시작, 삭제)은 별도 유스케이스로 간주하여 평가에서 제외

### 범위 감지 규칙

1. **단일 도메인 집중**: 요구사항 제목이 특정 도메인을 지칭하면 해당 도메인만 평가
2. **플로우 명시**: "플로우"가 명시된 경우 포함된 도메인만 평가 (결제 플로우 = Payment + Subscription)
3. **미래 기능 제외**: 갱신, 환불, 취소, 삭제는 별도 유스케이스로 간주
4. **필수 항목만**: 현재 플로우에 필요한 요구사항만 평가

## 1차원: 요구사항 완결성 (5점 만점)

LLM이 코드 생성 시 누락을 방지하기 위해 요구사항이 얼마나 명확한지 평가합니다.

| 항목 | 점수 | 평가 기준 |
|-----|-----|----------|
| Actor 식별 | 1점 | 핵심 Actor(사용자, 시스템)가 명확히 식별됨 |
| 유스케이스 명시 | 1점 | 주요 기능 흐름이 구체적으로 명시됨 |
| 비즈니스 불변식 구체성 | 1점 | "유효해야 한다"가 아닌 "0원 이상이어야 한다" 수준 |
| 예외/경계 조건 | 1점 | 실패 시나리오, 경계값 처리가 명시됨 |
| 도메인 용어 일관성 | 1점 | 유비쿼터스 언어가 일관되게 사용됨 |

### 등급 기준 (요구사항 완결성)

| 등급 | 점수 | 설명 |
|-----|-----|------|
| Excellent | 5점 | 불명확한 지점 없음, 바로 코드 생성 가능 |
| Good | 4점 | 사소한 불명확한 지점 있음 |
| Fair | 2-3점 | 핵심 불명확한 지점 있음, 추가 질문 필요 |
| Poor | 0-1점 | 요구사항 부족, 재작성 필요 |

### 불명확한 지점 식별 시 추가 질문 생성

**범위 내 필수 질문만 생성**
- 사용자가 명시한 범위 내에서만 질문 생성
- 갱신, 환불 등 별도 유스케이스는 제외
- 질문 생성 전 "이 질문이 현재 범위 내인가?" 확인

❌ Bad: 구독 결제 플로우에 갱신, 환불 질문 포함
✅ Good: 결제 검증, 구독 생성 관련 질문만 포함

요구사항 완결성이 낮을 경우 SKILL이 자동으로 추가 질문 목록을 생성합니다:

```
### 추가 질문 목록

❌ Fair (2/5) - 불명확한 지점 있음 → 추가 질문 필요

Q1: 모의고사 재시작 시 기존 답안은 어떻게 처리하나요?
    - 기존 답안 초기화
    - 기존 답안 보존
    - 사용자에게 선택권 제공

Q2: 시험 시간 만료 후 자동 제출되나요, 아니면 수동 제출만 가능한가요?

Q3: 모의고사 생성 시 같은 문제가 중복으로 포함될 수 있나요?
```

## 2차원: DDD 설계 품질 (10점 만점)

주어진 요구사항을 DDD 관점에서 얼마나 잘 설계했는지 평가합니다.

| 항목 | 점수 | DDD 관점 |
|-----|-----|----------|
| Aggregate 식별 | 1점 | Aggregate Root + Child Entity 명확성 |
| 경계 명확성 | 1점 | Aggregate 간 ID 참조만 사용 |
| 도메인 이벤트 | 1점 | 상태 변경 시 Event 발행 |
| 불변성 보장 | 1점 | Value Object 활용 |
| 유비쿼터스 언어 | 1점 | 도메인 전문가 용어 사용 |
| 비즈니스 불변식 | 1점 | Business Invariant 명시 |
| CQRS 분리 | 1점 | Command/Query 명확히 구분 |
| 도메인 서비스 분리 | 1점 | Entity에 속하지 않는 로직 분리 |
| 리포지토리 추상화 | 1점 | 기술 구현 감춤 |
| 컨텍스트 매핑 | 1점 | Bounded Context 간 관계 |

### 등급 기준 (DDD 설계 품질)

| 등급 | 점수 | DDD 품질 |
|-----|-----|----------|
| Excellent | 9-10점 | Rich Domain Model |
| Good | 7-8점 | Healthy Domain |
| Fair | 5-6점 | Anemic Domain Model 위험 |
| Poor | 3-4점 | Transaction Script |
| Incomplete | 0-2점 | 설계 부족 |

```
## 평가 결과

### 1차원: 요구사항 완결성 (3/5) - Fair
❌ 불명확한 지점 있음 → 추가 질문 필요
- Q1: 모의고사 재시작 시 기존 답안은 어떻게 처리하나요?
- Q2: 시험 시간 만료 후 자동 제출되나요?

### 2차원: DDD 설계 품질 (8/10) - Good
✅ Aggregate 식별, 경계 명확성, CQRS 등 잘 적용됨
⚠️ 도메인 이벤트 고려 필요

### 종합 평가
- 요구사항을 명확화한 후 DDD 구현을 권장
- 추가 질문에 답변하면 Rich Domain Model 구현 가능
```

## 워크플로우

1. 요구사항 분석
2. **요구사항 완결성 평가 (5점)**

   - **추가 질문 목록 생성**
3. **DDD 설계 품질 평가 (10점)**
   - 10개 항목 점수화
4. **2차원 종합 평가**
   - 요구사항 명확화 권장
   - DDD 패턴 개선 제안
